# beom-workbench

[English](README.md) | **한국어** | [日本語](README.ja.md) | [简体中文](README.zh-CN.md)

**코딩 에이전트의 작업대 — 기획하고, 요청이나 참고 저장소로 만들고, 승인한 합격 기준대로 되는지 검증합니다**


> 앱 화면은 한국어·영어·일본어·중국어(간체)를 지원합니다. 처음에는 시스템 언어를 따르고(그 밖의 언어면 한국어), 사이드바의 언어 단추로 바꿀 수 있습니다. 에이전트가 쓰는 언어는 에이전트 자체 규칙을 따릅니다 — 요청 언어가 분명하면 그 언어로 쓰라고 알려 주고, 알 수 없거나(첨부·링크뿐) 에이전트 설정에 응답 언어를 정해 두었으면(Claude Code `language`) 그 설정을 따릅니다. 명령줄 도움말(`--help`)과 설치 스크립트 안내도 같은 언어를 따릅니다.

![version](https://img.shields.io/badge/version-0.3.1-blue) [![smoke](https://github.com/ParkBeomsoo/beom-workbench/actions/workflows/ci.yml/badge.svg)](https://github.com/ParkBeomsoo/beom-workbench/actions/workflows/ci.yml) ![python](https://img.shields.io/badge/python-3.11%2B-blue) ![license](https://img.shields.io/badge/license-use%20only%2C%20no%20modification-lightgrey)

에이전트가 "다 됐다"고 할 때까지 맡기는 대신, 요구사항과 합격 케이스를 먼저 정하고, 에이전트는 자기 브랜치에서만 일하게 하고,
결과가 그 기준을 채우는지(옮겨 오는 경우 원본과 같은 동작인지) 프로그램으로 확인합니다. 분석 결론에는 모두 근거(파일:줄)가 붙습니다. Claude Code 같은 AI 에이전트가 절차를 따라 쓰도록
스킬·MCP 도구·CLI 를 함께 제공하고, AI 가 혼자 정하면 안 되는 일은 사람 승인 없이는 끝나지 않게 막습니다.

## 무엇을 하나

| 하고 싶은 일 | 툴킷이 하는 일 |
|---|---|
| **기능을 빠짐없이 파악** | 모든 파일을 분류하고 모든 함수를 검토 단위로 나눠, 결론마다 근거(파일:줄)를 붙입니다. 확정하지 못한 것은 "미확인 목록"으로 남깁니다. |
| **실제 API 목록** | 프레임워크별 규칙으로 HTTP·CLI 진입점을 찾고, 코드에서 조립되는 URL 까지 펼쳐 실제 경로 목록을 만듭니다. |
| **고치기 전 영향 확인** | 바꾸려는 함수가 어디에 영향을 주는지(호출자·구현체·진입점·테스트), 코어를 건드리지 않고 끼울 수 있는 확장 포인트가 어디인지 보여 줍니다. |
| **원본 업데이트 따라가기** | 두 버전을 비교해 우리 수정과 부딪히는 곳(함수 삭제·이름 변경·시그니처 변경)을 찾습니다. |
| **기능만 골라 옮기기** | 진입점 하나에서 필요한 코드·상태·설정·외부 의존을 잘라 내고, 항목마다 어디로 옮겼는지 원장에 기록합니다. 다른 언어로 다시 만들어도 됩니다. |
| **옮긴 결과 검증** | 같은 입력을 원본과 내 코드에 넣어 결과를 비교합니다(HTTP·CLI·함수 단위). 일부러 바꾼 동작은 기대값과, 원본에 없는 새 동작도 기대값으로 검증합니다. |
| **원하는 기능 만들기** | 참고할 원본 없이 "이런 기능을 만들어 줘" 에서 시작해, 요구사항과 합격 기준을 먼저 승인받고 만든 뒤 기준대로 됐는지·이상한 입력에도 버티는지 검증합니다. |
| **AI 지름길 차단** | 차이 허용·기능 생략·테스트 축소·기대값은 사람 승인 전까지 완료가 안 됩니다. 검증 뒤 코드가 바뀌거나 기록을 툴킷 밖에서 고치면 잡아냅니다. |

## 네 가지 모드 — 언제 무엇을

| 모드 | 이럴 때 | 결과 | 사람이 확인하는 것 |
|---|---|---|---|
| **요청사항으로 만들기** | 무엇을 만들지 안다 ("쇼핑몰 검색 페이지", "API 추가") — 새로 또는 기존 저장소 안에 | 요구사항 → 합격 기준 → 계획 → 코드 → 기준대로 검증 | 처음에 한 번(기준+계획 한 장) 또는 마지막에 한 번 |
| **레퍼런스로 만들기** | 다른 저장소(오픈소스·사내)에 이미 있고, 그대로 옮기거나 참고해 우리 식으로 다시 만들고 싶다 | 원본 분석 → 범위 → 케이스(원본 동작 또는 요청) → 코드 → 비교 | 위와 같음 + 차이 허용·생략은 승인 |
| **기획하기** | 아이디어가 아직 덜 정해졌거나, 개발 전에 디자인·QA 가 볼 기획이 필요하다 | 기획서·정책서(기존 정책 문서와 대조)·눌러 보는 화면 프로토타입·테스트 시나리오 | 질문 몇 개에 답 — 코드는 만들지 않음 |
| **자유 대화** | 작은 수정, 질문, 한 번 하고 끝낼 일 | 그 폴더에서 에이전트 CLI 를 그대로 (파일 수정·명령 실행도, 권한 규칙·작업 브랜치는 그대로) | 없음 — 절차 없이 |

서로 이어집니다: *기획* → **이 기획으로 만들기** 를 누르면 패키지 전체를 첨부한 *요청사항* 작업이 되고, *요청사항*·*레퍼런스* 작업은
언제든 메시지로 이어 갑니다. 어느 모드든 기존 저장소(또는 저장소 여럿이 든 상위 폴더)를 고르면 그 코드·규칙·화면 톤을 먼저 읽고
`feature/<작업명>` 브랜치에서 작업합니다.

## 지원 플랫폼

Windows 10/11 이 주 플랫폼입니다(매일 사용). macOS·Linux 도 같은 코드로 돌고, CI 가 세 OS 모두에서 설치·핵심 동작·앱 시작을 확인합니다.
네이티브 데스크톱 앱 화면 확인(Qt·WinForms·WPF)은 Windows 전용이고, Claude Code 의 OS 샌드박스는 macOS·Linux 에만 있습니다.

## 핵심 개념

**근거 등급** — 결론이 얼마나 확실한지를 등급으로 남깁니다.

| 등급 | 뜻 | 얻는 방법 |
|---|---|---|
| L0 | 코드를 읽고 구조 지도로 확인 | 기본 |
| L1 | 언어 서버로 호출·참조 확인 | `lsp` |
| L2 | 값이 어디서 어디로 흐르는지 확인 | `dataflow` |
| L3 | 실제로 실행되는 것을 확인 | 커버리지 리포트, 차등 검증 |

**원장** — 분석·포팅 상태는 프로젝트별 SQLite 원장(`~/.beom-workbench/projects/<id>/ledger.db`)에 쌓입니다.
세션이 바뀌어도, 여러 에이전트가 동시에 일해도 같은 기록을 이어 씁니다.

**포팅 완료 조건 (게이트 7개)** — 전부 충족해야 `port-finish` 가 완료 판정을 냅니다.

1. 옮길 항목이 모두 처리됨 (옮김 / 대체 / 생략)
2. 옮긴 위치가 지금도 그대로 있음 (줄 내용까지)
3. 차등 검증 통과 — 마지막으로 저장한 케이스 전부, **지금 코드 기준** (검증 뒤 코드가 바뀌면 무효)
4. 케이스가 옮길 함수를 모두 실행함 (원본 커버리지, 안 되면 내 코드 커버리지)
5. 사람 확인 항목이 모두 승인됨 (차이 허용·생략·케이스 변경·기대값, 승인 뒤 내용이 바뀌면 무효)
6. 기록이 툴킷 밖에서 바뀌지 않음 (원장 해시 사슬·골든 해시)
7. 옮길 코드에 제한형 라이선스가 없음 — 또는 사용자가 직접 확인함 (앱이 카드로 묻고, 에이전트는 대신 못 함). 라이선스 표기가 없는 것은 참고로만 알림

모든 포팅 명령 응답에는 `next_step`(다음에 할 일)이 붙습니다.

| 진입점 규칙 | Axum · Spring · Express · FastAPI/Flask · Gin · clap · Next.js (규칙이 없는 프레임워크는 자동으로 미확인 처리) |

## 설치

```bash
# 1. 툴킷 설치 — 어느 폴더에서나 beom-workbench 명령으로 쓸 수 있게
pipx install git+https://github.com/ParkBeomsoo/beom-workbench.git
# (또는) uv tool install git+https://github.com/ParkBeomsoo/beom-workbench.git

# 2. 상태 점검 — 엔진·언어 서버·스킬·MCP 등록
beom-workbench doctor

# 3. 엔진 설치 — 먼저 계획만 보고, 고른 것만 설치
beom-workbench setup --languages python typescript
beom-workbench setup --apply codebase-memory-mcp ast-grep lsp:python lsp:typescript coverage
```

- `setup` 은 아무 옵션 없이 실행하면 **계획만** 보여 주고 아무것도 바꾸지 않습니다. `--apply` 에 적은 것만 설치합니다.
- pipx·uv tool 로 설치해도 `setup` 이 넣은 도구(ast-grep 등)는 툴킷 옆에서 찾으므로 PATH 를 따로 고칠 필요가 없습니다.
- 남의 코드를 격리해서 실행하려면 컨테이너 엔진이 필요합니다. Windows 는 `setup --apply sandbox` 가 WSL 배포판 안에
  컨테이너 엔진을 설치합니다 (데스크톱 앱 불필요). 이미 `docker` 가 있으면 그것을 씁니다.
- JDK·Node.js·Go·Rust 같은 언어 런타임은 직접 설치합니다.

### AI 에이전트(Claude Code) 연동

둘 중 하나만 씁니다.

```bash
# A. setup 으로 스킬 + MCP 등록
beom-workbench setup --apply skill mcp-register
beom-workbench setup --apply skill mcp-register --scope project --project-dir <프로젝트>   # 한 프로젝트에서만

# B. Claude Code 플러그인 (툴킷은 위 1번으로 먼저 설치)
claude plugin marketplace add ParkBeomsoo/beom-workbench
claude plugin install beom-workbench@beom-workbench
```

- 스킬은 설치한 사본에 버전을 남겨, 툴킷이 업데이트되면 `doctor` 가 `outdated` 로 알려 줍니다.
- 같은 이름의 스킬을 직접 만들어 두었거나 다른 설치를 가리키는 MCP 등록이 있으면 덮어쓰지 않고 알려 줍니다.
- MCP 없이 CLI 만 써도 됩니다. 승인·완료 판정 같은 규칙은 CLI 에서도 똑같이 동작합니다.

### 업데이트와 제거

```bash
pipx upgrade beom-workbench
beom-workbench setup --update                      # 이미 설치한 스킬만 새 버전으로 (새로 설치하지 않음)
beom-workbench setup --remove skill mcp-register   # 이 툴킷이 설치·등록한 것만 되돌림
pipx uninstall beom-workbench
```

## 데스크톱 앱과 자동 실행

**Windows** (PowerShell) — pipx 가 없으면 설치하고, 앱과 필수 엔진까지 설치한 뒤 시작 메뉴·바탕화면 바로가기를 만들지 묻습니다:

```powershell
irm https://raw.githubusercontent.com/ParkBeomsoo/beom-workbench/main/install.ps1 | iex
```

**macOS · Linux**: `curl -fsSL https://raw.githubusercontent.com/ParkBeomsoo/beom-workbench/main/install.sh | sh`

다른 브랜치나 내려받은 폴더에서 설치하려면 먼저 `$env:BEOM_SOURCE = "git+https://github.com/ParkBeomsoo/beom-workbench.git@<브랜치>"`
(또는 폴더 경로)를 두고 같은 스크립트를 실행합니다. macOS·Linux 는 `BEOM_SOURCE=… sh install.sh`.

직접 설치:

```bash
pipx install "beom-workbench[app] @ git+https://github.com/ParkBeomsoo/beom-workbench.git"
beom-workbench                    # 앱 열기
beom-workbench app --shortcut          # 시작 메뉴(검색) + 바탕화면 바로가기 만들기, --remove-shortcut 으로 지움
```

앱을 처음 열 때도 바로가기를 만들지 물어봅니다. Linux 는 `.desktop` 항목을 만듭니다.

**홈에서 모드 고르기**

| 모드 | 이럴 때 | 진행 단계 |
|---|---|---|
| **요청사항 기반** | 이런 기능을 만들어 줘 (참고할 원본 없음) | 요구사항 → 합격 기준 → 계획 → 구현 → 검증 → 인수인계 |
| **레퍼런스 기반** | 다른 저장소의 기능을 내 프로젝트로 | 분석 → 범위 → 원본 기록 → 계획 → 구현 → 원본과 비교 → 인수인계 |
| **기획** | 기능·서비스를 개발·디자인·QA 에 넘길 기획 패키지로 | 파악 → 기획서 → 정책 → 화면 → 시나리오 → 점검·인계 → *이 기획으로 만들기* |
| **자유 대화** | 우리 절차 없이 Claude Code·Codex 를 그대로 | 메시지 → 작업 → 메시지 … |

**첨부** — 어느 모드든 기획서·문서·링크를 붙일 수 있습니다: md · txt · pdf · 이미지, 워드 · 파워포인트 · 엑셀 · 한글(HWPX)
(글로 바꾼 사본을 함께 넘김). 예전 바이너리 형식(.hwp · .doc · .ppt · .xls)은 읽을 수 없어 첨부할 때 거절하고, 새 형식으로 저장하는 방법을
알려 줍니다 (확장자를 바꿔도 내용으로 알아봅니다). 링크는 에이전트가 내용을 파악할 수 있게 가져옵니다 — 글만 납작하게 베끼지 않고, 제목·목록·표
(합친 칸 포함)·접힌 블록을 살린 마크다운으로 바꾸고, 그림과 첨부 파일은 받아서 같은 폴더에 둡니다 (워드·파워포인트·엑셀 첨부는 글로도 바꿈).
기획서는 표와 화면 설계 그림이 내용의 절반이기 때문입니다. 로그인이 필요한 페이지(컨플루언스·지라 등)는 앱이 로그인을 요청합니다 — 앱 안의
브라우저 창에서 로그인하고 **이 문서 가져오기** 를 누릅니다. 컨플루언스는 로그인한 그 세션으로 사이트의 REST API 를 읽어 본문과 함께 하위
페이지·댓글·첨부까지, 지라는 이슈의 설명·하위 작업·연결된 이슈·댓글·첨부까지 가져옵니다. 그 밖의 사이트는 페이지의 본문 영역을 같은 방식으로
바꿉니다. 로그인은 앱 전용 프로필에 남습니다 (**저장 공간 → 문서 로그인 기록** 에서 지움). 에이전트는 첨부를 먼저 읽습니다. 파일을 창에 끌어다 놓거나 스크린샷을 붙여 넣어도(Ctrl+V) 되고, 진행 중이거나 끝난 작업에 보내는 메시지에도 첨부할 수 있습니다 — 예) 고칠 곳의 스크린샷.

**기획 패키지** — 기획 모드는 문서 한 장이 아니라 기획자가 넘기는 묶음을 만듭니다 (대상 폴더의 `.beom/brief/`).

| 문서 | 내용 |
|---|---|
| 기획서.md | 목표·성공 지표, 사용자와 사용 장면, 기능 목록(P0·P1·P2), 요구사항 R1…, 범위 밖, 열린 질문·가정, 출시 단계 |
| 정책서.md | 조건별 결과 결정표, 계산 순서와 숫자 예시(경계값 포함), 상태 변화, 예외와 사용자에게 보일 문구 — 규칙마다 관련 R |
| 화면설계.md + wireframes/ | 화면 목록 S1…, 화면마다 번호 설명(①②)과 상태(기본·빈·오류·로딩), 흑백 와이어프레임 HTML — 툴킷이 스크린샷을 찍어 앱에 보여 줌 |
| 테스트시나리오.md | T1… — 요구사항마다 정상·경계·오류 시나리오. *이 기획으로 만들기* 에서 합격 케이스가 됨 |

인계 전에 툴킷이 문서끼리 맞물리는지 기계적으로 봅니다(`wb_brief_check`) — 시나리오가 없는 요구사항, 와이어프레임이 없는 화면,
빠진 문서·절이 있으면 인계할 수 없습니다. 문서는 '읽히는 것'이 먼저라, 맨 위 요약 상자·한 장 요약·표 위주로 짧게 쓰게 합니다.
앱의 *기획 패키지* 탭에서 문서를 넘겨 봅니다(*크게 보기*). **화면 설계는 눌러 보는 프로토타입**입니다 — 위에 기능별 탭(화면 목록 표의
'기능' 칸), 가운데 실제처럼 동작하는 화면(HTML), 오른쪽에 그 화면의 설명. 화면 안의 버튼·메뉴를 누르거나 탭·화면 칩을 누르면
화면이 바뀌고 설명도 따라 바뀝니다. 설명의 번호(①)를 누르면 화면에서 그 자리를 짚어 주고, 'S3' 같은 화면 번호를 누르면 그 화면으로 갑니다.
*내보내기* 로 공유용 파일을 만듭니다 — **HTML 한 파일**(문서마다 탭, 화면 설계는 같은 프로토타입 그대로 — 메일·메신저로 보내 브라우저로 열면 됨)
또는 **A4 PDF**(문서마다 새 쪽, 화면 설계는 화면 그림 + 설명). 프로토타입 화면은 앱과 떨어진 틀 안에서만 돌아 앱을 건드릴 수 없습니다.
이미 있는 정책서·기획 문서를 첨부하거나 기존 제품 폴더에서 기획하면, 그 정책·용어를 인용하고 바꾸는 부분만 '현행 → 변경'으로 쓰며,
화면 예시는 기존 화면의 톤앤매너를 따릅니다.
*이 기획으로 만들기* 를 누르면 패키지 전체(와이어프레임 포함)를 첨부한 요청사항 작업으로 넘어갑니다.

*레퍼런스로 만들기*(예전 이름 '오픈소스에서 가져오기')는 참고할 저장소 URL(또는 경로 — 오픈소스·사내 모두)만 필수입니다. 가져올 기능은
입력창에 말로 적거나, 비워 두면 에이전트가 기능 목록을 보여 주고 고르게 합니다. 원본과 똑같이 옮기는 포팅뿐 아니라 "이 기능을 참고해
우리 엔진 기준으로 새로" 같은 요청도 됩니다 — 그때는 원본에서 설계·동작 방식을 가져오고(근거: 원본 파일:줄) 합격 기준은 요청에서 정합니다.

**폴더** — 만들 곳을 안 고르면 문서 폴더 아래 새 폴더에 새로 만듭니다. 기존 코드에 넣으려면 그 저장소나, 저장소 여럿이 든 상위 폴더를
고릅니다 — 상위 폴더면 에이전트가 요청에 맞는 저장소를 찾아 그 안에서 작업합니다. *구조 참고* 는 만들 곳과 다른 저장소의
구조·명명·화면 톤을 따르게 할 때만 고릅니다 (만들 곳이 그 저장소면 안 골라도 됩니다).

**규칙·정책 문서** — 대화창에 붙이지 않아도 됩니다. 작업을 만들 때 대상 폴더에서 규칙 허브(rules·policies·guide 같은 이름의
폴더 README), AGENTS.md·CLAUDE.md, 정책·가이드·스토리보드 폴더를 찾아 에이전트에게 "먼저 읽고 따르라"고 넘깁니다 — 허브 README 에
작업 유형별 읽기 순서가 있으면 그 순서대로. 기존 정책이 우선이고, 정책에 없는 규칙은 '신규(추천)'으로 표시해 기존 조항과 부딪치지
않는지 근거와 함께 남깁니다. 기획 모드는 정책서에 '기존 정책 대조' 표(그대로 따름·변경·신규(추천)와 상충 여부)를 쓰고, 정책 문서가 있으면
점검에서 이 절을 요구합니다. 화면은 기존 제품이 있으면 그 톤앤매너(디자인 토큰·공용 컴포넌트·문구, 띄울 수 없으면 코드·가이드에서)를,
새로 만드는 것이면 같은 분야의 잘 만든 서비스를 조사해 컨셉을 정합니다 — 요청사항·레퍼런스·기획 모두. *자유 대화* 는 절차 없이
Claude Code·Codex CLI 를 그 폴더에서 그대로 쓰는 것과 같습니다 (대화만이 아니라 파일 수정·명령 실행도 하고, 권한 규칙은 그대로 적용).

**에이전트 · 모델 · 노력** — 보내기 버튼 옆 버튼 하나에서 고릅니다.

| Claude Code | 작업마다 툴킷 권한 규칙으로 확인. 모델은 Claude Code 가 계정 기준으로 받아 둔 목록에서 (Opus · Fable · Sonnet · Haiku 등, 이전 모델은 직접 입력), 노력 낮음 → 최대 — 모델별 기본값을 보여 줌 |

목록에 없는 모델 이름은 직접 입력합니다. 모델과 노력은 진행 중에도 바꿀 수 있습니다 (다음 라운드부터).

**권한** — 모드를 고르고, 종류별 세부 규칙은 *옵션 → 권한* 에 있습니다.

| 모드 | 동작 |
|---|---|
| 모두 물어보기 | 수정·명령마다 확인 |
| 편집 자동 허용 (기본) | 대상 폴더 안 수정, 빌드·테스트, 읽기만 하는 명령, 그 폴더의 자기 스크립트 실행은 바로, 그 밖의 명령(`python -c`·네트워크·폴더 밖 경로 등)과 웹은 확인 |
| 자동 | 명령·웹 조사도 묻지 않고 진행, 폴더 밖 파일만 확인 — 믿을 수 있는 작업에만. CLI 는 `beom-workbench run --permission auto` |

에이전트 자신의 임시 폴더(`%TEMP%/claude`)는 대상 폴더처럼 다룹니다 — 메모·임시 스크립트마다 묻지 않게.

push·배포·폴더 밖 삭제·시스템 변경은 언제나 거절합니다. 에이전트가 검증 도구에 넘기는 명령(케이스 파일 안의 명령 포함)도 같은 규칙을 거칩니다.
인증: *내 로그인*(구독) 또는 *API 키*(환경 변수의 키로 종량 과금) — 할 수 있는 일은 같습니다.

**기존 자산 기반** — 대상 폴더에 이미 코드·문서가 있거나(작업을 만들 때 스택·문서·화면 파일을 기록), 넣을 저장소·원본 저장소가 있으면
에이전트는 새로 만들기 전에 그것부터 파악해 맞춥니다: 같은 언어·프레임워크·구조, 정책 문서·검증 로직·문구의 업무 규칙,
기존 화면을 찍어 뽑은 톤앤매너(색·글꼴·컴포넌트·말투)와 기존 디자인 토큰. 요청사항·오픈소스·기획 모드 모두 같습니다.

**진행이 보이게** — 도는 중인 라운드는 '진행 중 · 지금 하는 일' 한 줄로 접혀 있고, 펼치면 지금까지 한 일(도구·메시지)이 보입니다.
라운드가 끝나면 '작업 과정'으로 접히고 마지막 보고만 남습니다. 단계는 기준·계획 → 확인 → 구현 → 검증 → 인수인계, 수락하면 모두 끝난 것으로 표시합니다.

**백그라운드** — 에이전트와 그것이 띄운 프로세스(개발 서버·감시 명령·만든 앱), 에이전트가 끝난 뒤 대상 폴더에서 남아 도는 것까지
머리줄의 *백그라운드* 칩에서 보고 끌 수 있습니다 (이 작업이 띄운 것만). 명령은 창 없이 돌아 터미널 창이 튀어나오지 않습니다.

**폴더** — 바탕 화면·문서·다운로드·홈·드라이브 맨 위를 고르면 그 안에 작업 이름으로 새 폴더를 만들어 그 안에서 만듭니다
(개인 파일이 기존 자산으로 잡히거나 결과물과 섞이지 않게).

**작업 브랜치** — 고른 폴더가 기존 git 저장소면 `main`(없으면 `master`)에서 `feature/<작업명>` 브랜치를 만들어 그 안에서만
작업합니다 (지금 브랜치는 그대로). 저장소 여럿이 든 상위 폴더면 에이전트가 고친 저장소마다 라운드가 끝날 때 같은 이름의 브랜치를 만들어
그 변경을 옮깁니다 — 손대지 않은 저장소는 그대로입니다. 라운드가 끝날 때마다 프로그램 변경을 그 브랜치에 커밋하고(툴킷 작업 폴더 `.beom/` 은 커밋하지 않음), 커밋하지 않은 채 있던 변경은 첫 커밋
'작업 전 변경'으로 따로 담습니다. 브랜치를 바꾸는 명령(switch·checkout <브랜치>·병합·pull·rebase·reset --hard·브랜치 삭제)은
권한 규칙 *작업 브랜치 밖으로* 가 막고, 라운드 앞뒤로 브랜치를 확인해 벗어났으면 되돌립니다 (못 되돌리면 멈춤).
지금 브랜치에서 바로 작업하려면 새 작업 화면의 *새 브랜치에서 작업* 을 끕니다. 저장소가 아닌 폴더(새로 만드는 프로젝트)는 그대로입니다.
에이전트는 합칠 수 없습니다. 합치기는 사용자가 합니다 — 실행 머리글의 브랜치 이름을 누르거나 `beom-workbench merge <실행> develop|main`.

**브랜치 흐름** — feature 는 언제나 깨끗한 `main`(로컬에 없으면 `origin/main`)에서 만듭니다. `develop` 은 실험 공간입니다: feature 를
`develop` 에 합쳐 시험하고, 적용은 그 *feature* 를 `main` 에 합칩니다. `develop` 자체는 `main` 이나 feature 에 합치지 않습니다. 지금 어디에
있든 새 작업은 막지 않습니다 — `develop` 이나 `develop` 커밋이 섞인 브랜치에 있어도 `main` 에서 깨끗한 feature 를 만들고, 거기 있던 커밋 안 된
변경은 실험이라 가져가지 않고 이름 붙인 stash 에 보관합니다 (그 브랜치에서 `git stash pop` 으로 되살림). 깨끗한 브랜치에서 하던 변경은 전처럼
함께 가져갑니다. 브랜치 이름의 합치기 메뉴는 작업 브랜치가 `develop`·`main` 에 이미 들어갔는지 보여 주고 **develop 에 합쳐 시험**·**main 에 적용**
을 제공합니다. 합치기는 체크아웃된 작업 폴더를 건드리지 않고(`git merge-tree` 로 결과를 만들어 대상 브랜치만 옮김), 충돌하면 아무것도 바꾸지 않고
충돌한 파일을 알려 주며, `develop` 커밋이 섞인 브랜치는 `main` 에 합치지 않고, 원격(push)에는 올리지 않습니다.

**사람이 정하는 것** — 이것만 카드로 뜹니다.

- **처음에 한 번 — 시작 전 확인**: 에이전트는 요구사항·합격 기준·계획을 한 번에 세우고(승인 전에는 화면·코드를 만들지 않음),
  개발자가 아니어도 무엇을 승인하는지 알 수 있게 한 장으로 뜹니다 — 무엇을 만들고 어떻게 여는지(2~3문장), 만들 것(요구사항),
  **정할 것**(형태 — 웹·앱·API, 데이터 저장, 실행 방법을 추천안 + 대안 + 이유로, 사용자에게 무엇이 달라지는지로), 디자인 컨셉(한두 줄),
  진행 순서(단계가 끝나면 보게 될 결과로). 합격 기준은 '무엇을 확인하는지'만 보이고, 어떻게 시험했는지는 *검증* 탭에 있습니다.
  대안을 눌러 바꾼 채 승인하면 바꾼 결정이 에이전트에게 전달되고, 그 결정에 맞춰 고친 요구사항·기준은 다시 묻지 않고 자동 승인됩니다.
  추천을 고를 수 있는 것은 따로 묻지 않습니다. 한 번 승인하면 완료 조건을 다 채울 때까지
  진행합니다. 카드마다: *승인*, *고치기*(요구사항·케이스·계획 단계를 직접 고친 뒤 *저장하고 승인* — 원장에 사용자 작성으로 남고
  에이전트에게도 전달), 또는 입력창에 고칠 점을 적기 (승인 없이 에이전트가 고침).
- 에이전트의 **질문**(번호·줄바꿈이 살아 있고, 선택지는 한 줄에 하나, *추천대로* 단추)과 **권한 요청** (`Y` 허용 · `N` 거절).
  묻고 답한 것은 대화 흐름에 그대로 남습니다.
- 마지막 **인수인계**: 수락하거나, 메시지를 보내 계속 — 멈췄거나 끝난 실행에 메시지를 보내면 이어서 진행합니다.
  추가 요청은 정해 둔 기준 위에서 고치고 관련 케이스만 다시 검증합니다 (범위가 바뀌는 요청이면 기준부터 고쳐 확인받음).
  수락했던 작업도 추가 요청이 끝나면 바뀐 결과를 다시 수락합니다. 기획·분석부터 다시 하려면 새 작업으로 시작합니다.
- 레퍼런스 모드에서 원본에 제한형 라이선스(카피레프트 등)가 있으면 **라이선스 카드**: 옮겨 써도 되는지 확인하면 완료 판정으로 넘어갑니다.
  그동안 에이전트는 라운드를 쓰지 않고 기다립니다. 라이선스 표기가 아예 없으면(사내 저장소는 보통 그렇습니다) 막지 않고 참고로만 보여 줍니다.

승인은 앱 안에서만, 화면에 보인 내용 그대로에 묶여 원장에 기록됩니다. 에이전트가 닿을 수 있는 승인 경로는 없습니다.

**오른쪽 패널**

| 탭 | 보이는 것 |
|---|---|
| 현황 | 진행률, 계획 단계, 요구사항, 완료 조건 |
| 기준 | 합의한 것 — 요구사항, 합격 케이스(입력 → 기대), 계획, 누가 언제 승인했는지 |
| 검증 | 검증한 것 — 요구사항별 케이스의 입력 → 기대 → 실제 결과, 완료 조건마다 무슨 뜻인지 |
| 변경 | 바뀐 파일과 diff, 파일별 되돌리기, 체크포인트 (라운드마다 대상 폴더를 기록해 아무 시점으로 되돌림) |

**라운드** — 에이전트 세션 한 번이 한 라운드이고, 실행기는 완료 조건을 다 채울 때까지 라운드를 이어 갑니다.
기본은 횟수 제한이 없고, 세 라운드 연속 진전(원장·계획·대상 폴더 변화)이 없으면 스스로 멈춥니다. *옵션* 에서 제한을 두거나, *마지막에 한 번 확인* 으로
만들고 검증까지 한 뒤에 확인할 수도 있습니다.

**라운드 규칙** — 실행 옵션 아래(모든 작업에 적용, 도는 중에 바꿔도 다음 판단부터 반영)나 `beom-workbench rounds` 로 정합니다.

| 규칙 | 기본 | 뜻 |
|---|---|---|
| `stall_rounds` 진전 없으면 멈춤 | 3 | 원장·계획·대상 폴더가 그대로인 라운드가 이만큼 이어지면 멈춤 (1~10) |
| `hard_rounds` 안전 상한 | 50 | '끝날 때까지'여도 이 라운드에서 멈춤 — 메시지를 보내면 이어 감 (5~500) |
| `round_idle_min` 무응답 라운드 끝내기 | 30분 | 에이전트가 이 시간 동안 아무 출력이 없으면 그 라운드를 끝냄 (5~240) |
| `round_max_min` 라운드 시간 상한 | 120분 | 출력은 나오는데 끝나지 않는 라운드를 이 시간에 끝내고 다음 라운드로 — 사람 답을 기다린 시간은 빼고 셈 (10~600) |
| `on_limit` 사용 한도에 걸리면 | wait | wait: 풀릴 때까지 기다렸다 같은 라운드를 다시 / stop: 멈추고 알림 |
| `limit_wait_max_min` 최대 대기 | 360분 | 이보다 늦게 풀리거나, 한도에 이어서 걸려 기다린 시간의 합이 이를 넘으면(무료 요금제의 주간 한도 등) 멈추고 알림 (10~1440) |
| `transient_retries` 일시 장애 재시도 | 5 | 과부하·네트워크 오류 재시도 횟수, 30초부터 두 배씩 최대 10분 간격 (0~10) |
| `fail_rounds` 연속 실패 | 2 | 아무것도 못 하고 오류로 끝난 라운드가 이만큼 이어지면 멈춤 (1~5) |
| `notify` 창 밖 알림 | all | 창이 뒤에 있을 때의 Windows 알림 — all · important(끝남·실패만) · off. 같은 작업은 창을 다시 볼 때까지 한 번만 띄우고, 그 사이엔 작업 표시줄만 깜빡임 |
| `cost_budget_usd` 비용 상한 | 0 (없음) | 작업 하나가 이 금액(달러)을 쓰면 멈춤, 이어서 누르면 다시 셈. 비용을 알려 주는 Claude Code 만 — 구독은 API 환산 금액 (0~1000) |

```
beom-workbench rounds                                   # 지금 값과 설명
beom-workbench rounds --set stall_rounds=5 on_limit=stop
beom-workbench rounds --reset                           # 모두 기본값으로
```

**라운드가 오류로 끝나면** — 진전 없음과 구분해서 처리하고, 오류로 끝난 라운드는 횟수에 넣지 않습니다.

| 원인 | 처리 |
|---|---|
| 사용 한도 (usage limit · 429 · quota) | 메시지에서 풀리는 시각을 읽어(모르면 5 → 10 → 20 → 30 → 60분) 기다렸다가 **같은 라운드를 다시** 시작. 상태는 *한도 대기*, 남은 시간이 보이고, 메시지를 보내면 바로 다시 시도. 규칙이 *멈춤* 이거나 최대 대기보다 늦게 풀리면 멈추고 풀리는 시각을 알림 |
| 일시 장애 (overloaded · 5xx · 네트워크·시간 초과) | 30초부터 두 배씩(최대 10분) 다시 시도, 정한 횟수를 넘으면 멈추고 알림 |
| 로그인 만료 · 잘못된 키 | 바로 멈추고 *로그인 필요* — 로그인 방법을 보여 주고, 로그인 뒤 이어서 진행 |
| 대화가 너무 길어짐 (context 초과) | 새 대화로 이어 감 — 진행 상황은 원장에서 다시 읽음 |
| 알 수 없는 오류로 아무것도 못 하고 바로 끝남 | 두 번 이어지면 멈추고 오류 문장을 보여 줌 (같은 실패를 되풀이하지 않게) |

승인을 기다리는 동안 질문에 답하면, 승인 전에 답을 기준·계획에 반영하는 라운드를 먼저 돕니다 — 답이 빠진 기준을 승인했다가 나중에 또 멈추지 않게.
승인한 계획에 적혀 있던 명령(예: `npm run test:coverage`)은 실행할 때 다시 묻지 않습니다 — 승인할 때 이미 본 명령이기 때문입니다.
계획에 없던 명령은 권한 규칙대로 묻습니다.

**화면과 디자인** — 화면이 있는 작업은 계획에 디자인 방향(톤·색·글꼴·참고·피할 것)이 함께 오고 기준과 같이 승인합니다.
에이전트는 흔한 'AI 티'를 피하는 디자인 규칙을 따릅니다. 화면 케이스는 실제 브라우저 엔진으로 페이지를 열어 글자·요소·스크립트 오류를
확인하고 스크린샷을 남깁니다 — 검증 탭에서 크게 볼 수 있습니다. 네이티브 데스크톱 앱(Qt · WinForms · WPF · WinUI 등, 지금은 Windows)은
앱을 띄워 접근성 정보(UI Automation)로 글자·컨트롤을 읽고, 값을 넣고 버튼을 누른 뒤 창 스크린샷을 남깁니다.

**데이터 저장 위치** — 모두 내 컴퓨터에 남습니다. [데이터와 저장 위치](#데이터와-저장-위치)를 보세요.

앱 없이: `beom-workbench run --mode request --target-root <폴더> --request "<요청>"` (`--agent codex`, `--resume <실행>`), 답은 앱에서 합니다.

Claude Code 는 [공식 안내](https://code.claude.com/docs)대로 설치하고 `claude auth login`, Codex 는 `npm i -g @openai/codex` 후 `codex login`
(확인: `beom-workbench agent-status`). 내 컴퓨터에서 본인이 쓰면 구독 로그인, 다른 사람에게 서비스하려면 API 키를 씁니다
([Anthropic 약관](https://code.claude.com/docs/en/legal-and-compliance)).

## 빠른 시작 1: 저장소 전수 분석

**AI 에이전트에게 맡길 때** — Claude Code 에서:

> 이 저장소 전수 분석해줘 https://github.com/<조직>/<저장소>

스킬이 아래 절차를 따라 진행하고, 큰 저장소는 서브에이전트 여러 개가 단위를 나눠 병렬로 분석합니다.

**CLI 로 직접 할 때**

```bash
beom-workbench open https://github.com/<조직>/<저장소> --ref v1.2.0   # 분석 전용 clone, 커밋 고정 → project_id
beom-workbench inventory <pid>                    # 파일 분류·심볼·구조 지도·진입점·분석 단위
beom-workbench features <pid>                     # 실제 URL·CLI 진입점 목록

# 분석 루프 (단위가 없을 때까지 반복)
beom-workbench next <pid> --agent a1              # 다음 단위 받기
beom-workbench context <pid> <unit_id> --agent a1 --raw
beom-workbench finding <pid> <unit_id> --agent a1 --json finding.json   # 결론 + 근거
beom-workbench unknown-add <pid> --agent a1 --json unknown.json        # 확정 못 한 것
beom-workbench complete <pid> <unit_id> --agent a1 --summary "이 단위가 하는 일"

beom-workbench coverage <pid>                     # 파일·심볼 2축 완료율과 실패 항목
beom-workbench unknowns <pid>                     # 남은 미확인
beom-workbench export <pid>                       # Markdown + JSON 리포트
```

`finding.json` 예:

```json
{"text": "주문 생성 시 재고를 먼저 잠그고 결제 실패 시 해제한다", "severity": "important",
 "evidence": [{"path": "src/order/service.rs", "start_line": 120, "end_line": 158}],
 "symbol_ids": ["s_1a2b3c"]}
```

## 빠른 시작 2: 기능 옮기기와 검증

예: 원본의 `POST /api/v1/orders` 를 내 저장소에 다른 언어로 옮기는 경우.

```bash
# 1. 옮길 범위 보기 → 포팅 원장 만들기
beom-workbench slice <pid> "POST /api/v1/orders"
beom-workbench port-create <pid> --name 주문 --targets "POST /api/v1/orders" --language javascript --target-root <내 저장소>

# 2. 원본 응답 저장 (골든) — 원본은 컨테이너에서 격리 실행
beom-workbench port-capture <pid> <port_id> --cases cases.json \
    --source-image <원본 실행 이미지> --source-url http://127.0.0.1:18001 --source-cmd "<원본 서버 실행 명령>" \
    --coverage-cmd "<커버리지 리포트 생성 명령>" --coverage-report cov.json --explore 40

# 3. 내 코드 작성 → 항목마다 어디로 옮겼는지 기록
beom-workbench port-map <pid> <port_id> --json map.json

# 4. 비교 검증 (동시 요청까지)
beom-workbench port-verify <pid> <port_id> --target-url http://127.0.0.1:18002 --target-cmd "node server.js" --concurrency 8

# 5. 진행 상황과 다음 할 일
beom-workbench port-status <pid> <port_id>

# 6. 사람 승인 — 사용자가 터미널에서 직접 실행 (에이전트가 대신 실행하면 거부됨)
beom-workbench port-approve <pid> <port_id>

# 7. 완료 판정 — 게이트 7개가 모두 충족될 때만 발급
beom-workbench port-finish <pid> <port_id>
```

`map.json` 예 — 옮김(`ported`)은 내 코드의 `경로:줄`, 대체·생략은 사유가 필요합니다.

```json
[{"item": "s_1a2b3c", "status": "ported", "target": "src/orders/create.js:12"},
 {"item": "s_4d5e6f", "status": "replaced", "note": "원본 큐 대신 기존 메시지 서비스 사용"},
 {"item": "s_7a8b9c", "status": "omitted", "note": "관리자 통계는 이번 범위 밖"}]
```

**옮긴 기능을 바꿔서 가져오기**

| 상황 | 방법 | 판정 |
|---|---|---|
| 원본과 같아야 함 | 케이스만 작성 | 원본 응답과 비교 |
| 일부러 다르게 만듦 (값을 정할 수 있음) | 케이스에 `expect` | 원본 대신 기대값과 비교, 기대값은 사람 승인 |
| 원본에 없는 새 동작 | `"new": true` + `expect` | 원본은 실행하지 않고 기대값으로 판정 |
| 형식만 다르고 값은 못 정함 | `port-accept --case <이름> --reason "<사유>"` | 차이 허용 제안 → 사람 승인 |
| 기능 일부를 뺌 | `port-map` 에서 `omitted` + 사유 | 사람 승인 |

- 승인 화면에는 원본 응답과 기대값(또는 실제 차이)이 나란히 나옵니다. 승인 뒤 내용이 바뀌면 다시 승인해야 합니다.
- 원본을 커버리지로 계측할 수 없으면 `port-verify --target-coverage-cmd ... --target-coverage-report lcov.info` 로 내 코드 쪽 실행 범위를 잽니다.
- 내 코드를 고쳐 줄이 밀리면 `port-map --follow` 로 옮긴 위치를 갱신합니다.

## 빠른 시작 3: 요청사항으로 만들기

앱에서 **요청사항 기반** 을 고르거나, CLI 로:

```bash
beom-workbench make-create --name 주문총액 --request "수량을 받아 총액 계산. 개당 2000원, 10개 이상 10% 할인, 0 이하면 400" --target-root <폴더>
beom-workbench make-req <pid> <port_id> --json reqs.json          # [{"text": "총액 = 수량 x 2000원"}, …] → R1, R2 …
beom-workbench port-capture <pid> <port_id> --cases cases.json --explore 20   # 요구사항마다 expect + req
beom-workbench port-approve <pid> <port_id>                       # 구현 전에 요구사항·합격 기준 승인
beom-workbench port-map <pid> <port_id> --json map.json           # 요구사항 → 구현 위치 "경로:줄"
beom-workbench port-verify <pid> <port_id> --target-url http://127.0.0.1:8080 --target-cmd "<서버 실행 명령>"
beom-workbench port-finish <pid> <port_id>
```

- 케이스마다 `req`(확인하는 요구사항)와 `expect`(기대값)가 필요하고, 요구사항마다 케이스가 하나 이상 있어야 합니다.
- 입력 자동 변형 케이스는 기대값 대신 **죽지 않음·5xx 아님** 으로 판정합니다 (이상한 입력은 4xx 로 거절해야 통과).
- 넣을 저장소가 있으면 먼저 `open`·`inventory` 해서 `--context <그 project_id>` 로 넘기면 기존 구조에 맞춰 만듭니다.

## 원본을 고쳐 쓰는 경우 (커스텀)

```bash
beom-workbench extpoints <pid>                                  # 코어를 안 건드리고 끼울 수 있는 곳 먼저
beom-workbench impact <pid> pricing.calc_total --verify         # 바꾸면 영향받는 진입점·테스트·결론
beom-workbench custom-add <pid> --description "할인 계산 변경" --kind modify --targets pricing.calc_total

# 원본 새 버전이 나오면
beom-workbench open <저장소> --ref v1.3.0 && beom-workbench inventory <새 pid>
beom-workbench compare <기준 pid> <새 pid> --save                # 바뀐 곳 + 우리 수정과 부딪히는 곳
```

고친 원본을 원래 원본과 비교 검증하려면, 고친 저장소를 `--target-root` 로 두고 [빠른 시작 2](#빠른-시작-2-기능-옮기기와-검증) 와 같은 방법으로 검증합니다.

## 케이스 파일 형식

```json
{
  "defaults": {"headers": {"Content-Type": "application/json"}},
  "cases": [
    {"name": "주문생성", "method": "POST", "path": "/api/v1/orders", "json": {"sku": "A1", "qty": 2},
     "match": {"id": "[0-9a-f]{32}"}, "ignore": ["createdAt"]},
    {"name": "주문조회", "method": "GET", "path": "/api/v1/orders/{{주문생성.id}}"},
    {"name": "수량0", "method": "POST", "path": "/api/v1/orders", "json": {"sku": "A1", "qty": 0}, "compare": "status"},
    {"name": "할인적용", "method": "POST", "path": "/api/v1/orders", "json": {"sku": "A1", "qty": 10},
     "expect": {"status": 201, "equals": {"total": 18000}}},
    {"name": "쿠폰_새기능", "new": true, "method": "POST", "path": "/api/v1/orders",
     "json": {"sku": "A1", "qty": 1, "coupon": "WELCOME"}, "expect": {"equals": {"discount": 1000}}}
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `method`·`path`·`json`·`headers` | HTTP 케이스 |
| `argv`·`stdin` | CLI 케이스 |
| `call: {source, target}`·`args`·`kwargs` | 함수 단위 비교 (`경로:함수명`, 언어가 달라도 됨) |
| `{{케이스이름.필드}}` | 앞 케이스 결과 값 사용 (이름에 공백 없이) |
| `ignore` | 비교하지 않을 경로 (`items.*.t`) |
| `match` | 값 대신 정규식으로 확인 (id·시간처럼 매번 다른 값) |
| `compare: "status"` | 상태 코드만 비교 |
| `expect` | 원본 대신 기대값과 비교 — `status`·`body`·`equals`(경로: 값, 배열은 `items.0.price`)·`match` |
| `new: true` | 원본에 없는 동작 (`expect` 필수, 원본에서는 실행 안 함) |
| `screen: {path \| file, mobile}` · `expect: {visible, selectors, no_errors}` | 화면 케이스 — 페이지를 열어 글자·요소·스크립트 오류를 확인하고 스크린샷을 남김 |
| `screen: {app, actions, title}` · `expect: {visible, selectors: ["Button:계산"], no_errors}` | 네이티브 앱 화면 (Windows) — `app` 은 실행 파일·명령, `actions` 는 `{"set": "Edit:수량", "value": "10"}` · `{"click": "Button:계산"}`. selectors 는 "종류:이름", no_errors 는 앱이 죽지 않고 표준 오류에 예외가 없음. 앱 실행 명령도 명령 규칙을 거침 |
| `description` | 무엇을 확인하는지 사람이 읽는 설명 — 이름 대신 보임 |
| `explore: false`·`concurrent: false` | 입력 자동 변형·동시 요청 검사에서 제외 |

표에 없는 키는 저장할 때 거절합니다 (`argv` 대신 `args` 처럼 잘못 쓴 키가 조용히 무시되면 다른 입력으로 검증되기 때문). 요청사항 모드는 케이스마다 `req` 도 필요합니다.

## 데이터와 저장 위치

Claude Code(`~/.claude`)·Codex(`~/.codex`)처럼 홈 아래 폴더 하나(`~/.beom-workbench`, `BEOM_WORKBENCH_HOME` 으로 변경)에 모으고,
안은 성격별로 나눕니다. 어디로도 보내지 않고, 비밀은 저장하지 않습니다 — 키·토큰은 환경 변수로만 읽고 출력에서는 가립니다.

| 폴더 | 내용 | 지워도 되나 |
|---|---|---|
| `settings.json` | 사용자 설정 (정리 주기, 기본값) | 됨 — 기본값으로 |
| `projects/<id>/` | 분석·포팅 원장 `ledger.db`(SQLite, 스키마 버전, 해시 사슬), 고정 커밋의 원본 클론, 골든 응답 | **안 됨** — 승인·검증 기록 |
| `runs/<실행>/` | 자동 실행 하나 = 대화 하나: `run.json` 상태, `events.jsonl` 흐름(추가만), `inbox/` 질문·승인 요청, `shadow.git` 대상 폴더 체크포인트, `agent/` 라운드마다 다시 만드는 에이전트 설정 | 휴지통으로 |
| `trash/` | 지운 실행, 7일 뒤 자동으로 비움 | 됨 |
| `app/` | 바로가기가 가리키는 앱 아이콘 | 안 됨 |
| `cache/` · `cbm-cache/` | 에이전트 상태, 검증 하네스, 구조 지도 색인 | 됨 — 다시 만듦 |
| `work/` | 검증·커버리지용 임시 사본, 쓰고 바로 지움 (6시간 넘게 남은 것은 시작할 때 정리) | 됨 |
| `bin/` · `engines/` · `node/` | `setup` 이 설치한 분석 엔진 | 됨 — `setup` 으로 다시 설치 |

에이전트와의 대화 원본은 각 CLI 가 원래 두는 곳(`~/.claude/projects`, `~/.codex/sessions`)에 있고 세션 id 로 이어 갑니다.
대상 폴더에는 툴킷 작업 파일을 `.beom/` 에 둡니다 (합격 케이스·기획 문서·스크린샷). 커밋하지 않습니다 — 커밋은 프로그램만 —
git 저장소면 그 저장소의 로컬 제외 목록에 넣어 `git status` 에도 보이지 않게 합니다.

| | Claude Code | Codex | 이 툴킷 |
|---|---|---|---|
| 대화 | `projects/<폴더>/<세션>.jsonl` | `sessions/YYYY/MM/DD/*.jsonl` | `runs/<실행>/events.jsonl` (+ 에이전트 자체 대화 기록) |
| 설정 | `settings.json` | `config.toml` | `settings.json` |
| 상태 | 파일 변경 기록(체크포인트) | 버전 붙은 SQLite | 프로젝트별 SQLite 원장(스키마 버전, 해시 사슬) + 실행별 git 체크포인트 |
| 정리 | 기본 30일 지난 대화 자동 삭제 | 보관 | 기본 보관, 원하면 끝났거나 숨긴 실행을 30/90일 뒤 자동 정리, 휴지통은 7일 뒤 비움 |

실행을 지워도 승인·검증 결과는 지워지지 않습니다 — 프로젝트 원장에 남습니다. 휴지통을 비우면 그 실행들만 쓰던 요청사항 원장도 함께 지우고,
어느 실행도 쓰지 않는 다른 원장은 **저장 공간** 에 크기와 함께 보여 줘 직접 지우게 합니다 (에이전트가 직접 분석한 원장일 수 있어서). 앱이 시작할
때 14일 지난 링크 문서(실행을 시작할 때 대상 폴더로 복사됨)와 그 밖에 남은 임시 파일도 정리합니다.

```bash
beom-workbench data                        # 어디에 무엇이 얼마나
beom-workbench data --trash <실행>          # 실행을 휴지통으로 (--restore <이름>, --empty-trash)
beom-workbench data --prune 30 --dry-run   # 30일 동안 그대로인 끝났거나 숨긴 실행
beom-workbench data --set-cleanup 30       # 시작할 때 자동 정리 (0 = 끔)
beom-workbench data --delete-project <id>  # 어느 실행도 쓰지 않는 원장 지우기
beom-workbench data --clear-browser        # 문서 링크에 쓴 사이트 로그인 지우기
beom-workbench data --revoke-sandbox       # Windows: 격리 실행에 준 폴더 권한 거두기
```

앱에서는 사이드바 아래 **저장 공간**, 실행의 ⋯ 메뉴 **휴지통으로**.

## 안전 원칙

- **분석 대상 코드는 실행하지 않습니다.** 언어 서버의 빌드 스크립트·매크로 실행도 끕니다. 실행이 필요한 검증(커버리지·포팅 원본)은
  컨테이너(네트워크 차단)에서, 또는 사용자가 신뢰한다고 한 저장소만 임시 사본에서 실행합니다.
- **비밀 파일은 읽지 않고**, 일반 파일 속 비밀값(비밀번호·키·토큰·URL 자격 증명)은 출력할 때 `****` 로 가립니다.
  실행 환경 변수에서도 토큰·키류는 빼고 넘깁니다.
- 분석은 **전용 clone 의 고정 커밋**에서만 합니다. 작업 중인 원본 폴더의 미커밋 변경은 반영되지 않습니다.
- 포팅의 사람 승인은 데스크톱 앱, MCP 확인 창, 사용자의 터미널 입력으로만 받습니다 — 자동 실행 중인 에이전트에게서는 받지 않습니다.
- **에이전트는 자기 작업을 승인할 수 없습니다.** 사용자 계정으로 돌기 때문에 자기가 쓴 코드를 테스트·빌드로 실행하면 툴킷 기록을 직접
  고칠 수 있고, 같은 계정에서는 열쇠·서명으로도 막을 수 없습니다. 그래서 앱이 유일한 권한자입니다 — 앱에서 내린 결정을 기억하고,
  라운드 앞뒤로 계획 승인·권한 규칙·수락·원장 승인을 비교해 앱이 하지 않은 변경이면 되돌릴 수 있는 것은 되돌리고, 사용자가 확인할
  때까지 멈춥니다.
- **격리 실행(샌드박스).** 에이전트가 실행하는 명령은 운영체제가 대상 폴더·임시 폴더·흔한 도구 캐시(npm·pip·cargo·Gradle·Maven·Go·NuGet)
  에만 쓰게 막습니다 — 그 밖(툴킷 기록 포함)에 쓰면 "액세스 거부"로 실패합니다. 처음 설정의 한 항목입니다: 에이전트 목록에
  **격리 실행 · 준비됨** 으로 나오고, 빠진 게 있으면 **구성** 버튼이 나옵니다 (**한 번에 설치** 에도 포함).

  | 플랫폼 | Claude Code | Codex | Gemini (agy) |
  |---|---|---|---|
  | Windows | Claude 자체 샌드박스가 Windows 에서 꺼져 있어, Claude 가 PowerShell 로 명령을 실행하게 하고 허용된 명령을 앱에 든 Windows 격리 실행으로 돌립니다 — 쓰기 제한 토큰, 관리자 권한·설치 필요 없음 (Windows Home 에서도 동작) | 자체 샌드박스 | `--sandbox` |
  | macOS | Claude Code 내장 샌드박스(Seatbelt)를 앱이 켭니다 — 설치할 것 없음 | 자체 샌드박스 | `--sandbox` |
  | Linux | Claude Code 샌드박스 (`bubblewrap`·`socat` 필요, 설정에서 설치) | 자체 샌드박스 | `--sandbox` |

  Windows 격리 실행의 원리: 명령은 내 토큰을 '쓰기 제한'으로 줄인 것(특권 모두 제거)으로 돌아, 쓰기는 격리 전용 신원에게도 허락돼야 합니다.
  앱이 대상 폴더·임시 폴더·쓰는 도구 캐시에만 그 신원의 *수정* 권한을 줍니다 (그 폴더에 남고, `%LOCALAPPDATA%\beom-workbench-sandbox\granted.txt` 에
  기록). 읽기는 그대로라 빌드·테스트는 평소처럼 됩니다. Windows 에서는 이 방식으로 네트워크를 막을 수 없어 *웹* 권한 규칙이 정합니다.
  Git Bash 는 제한 토큰에서 시작하지 못해 Claude 는 PowerShell 을 씁니다. 직접 확인: 안쪽 쓰기 성공, 바깥·`~/.beom-workbench` 쓰기 거부
  (권한 규칙이 못 보게 실행 중에 경로를 만들어도 거부), `npm install`·`node`·`python`·`pip`·`git` 동작, 창이 뜨지 않음. macOS·Linux 는 샌드박스 밖 재실행을 막고, 웹 허용일 때도 패키지 저장소에만 접속합니다. 전역 설치(`npm -g`·`pip --user`)는
  일부러 막힙니다. 실행 옵션에서 작업마다 끌 수 있습니다.
- **권한 규칙** 이 에이전트의 모든 도구·명령을 나눕니다 — 대상 폴더 안 수정, 빌드·테스트, 그 밖의 명령, 웹, 폴더 밖, 게시(push·패키지
  게시·PR 생성), 폴더 밖 삭제, 시스템 변경(레지스트리·예약 작업·git 설정·에이전트 자신의 `.claude/`·`.git/` 설정), 작업 브랜치 밖으로.
  게시·폴더 밖 삭제·시스템 변경·브랜치 바꾸기는 모든 모드에서 거절합니다.
- **기존 저장소는 새 브랜치에서** (`main` 에서 `feature/<작업명>`, `develop` 에서는 만들지 않음) 라운드마다 커밋하고, 앱이 하는 커밋은 저장소 훅을 돌리지 않습니다.
  커밋 안 된 변경은 첫 커밋으로 따로 담습니다.
- 기록에 남는 명령·도구 입력의 토큰·키·접속 문자열 비밀번호는 가립니다.

## 문제 해결

| 증상 | 원인과 해결 |
|---|---|
| 설치했는데 에이전트가 **설치 필요** 로 나온다 | 대개 PATH 문제입니다 (예: `nvm use` 로 Node 를 바꿔 npm 으로 깐 CLI 가 빠짐). 앱은 확인할 때마다 PATH 를 다시 읽고, Codex 는 npm 패키지 안의 네이티브 실행 파일을 바로 써서 Node 버전과 상관없이 돕니다. 정말 없으면 **설치**(공식 단독 설치, Node 필요 없음) 또는 **없는 에이전트 한 번에 설치** 를 누릅니다. |
| **로그인 필요** | **로그인** 을 누르면 터미널이 열립니다 — 마치고 돌아오면 다시 확인합니다. |
| **격리 실행 · 구성 필요** | Linux 에서 `bubblewrap`·`socat` 이 없습니다 — **구성** 을 누릅니다. Windows 는 앱에 들어 있고 macOS 는 기본 내장이라 설치할 것이 없습니다. |
| Ubuntu 24.04 이상에서 설치 후에도 **격리 실행 · 구성 필요** | `bubblewrap` 은 깔렸지만 AppArmor 가 필요한 사용자 이름공간을 막습니다 (26.04 는 `bubblewrap` 안에서도). 앱은 실제로 샌드박스를 띄워 확인합니다. **구성** 을 누르면 시스템 전체에서 그 제한을 풉니다 (관리자 암호, 다시 켜도 유지): `kernel.apparmor_restrict_unprivileged_userns=0` 을 설정하고, 있으면 `bwrap-userns-restrict` 프로필을 끕니다. |
| **분석 엔진 · 설치** 가 *rate limit* 으로 실패 | 회사망처럼 여러 PC 가 주소 하나를 쓰면 GitHub API 의 시간당 한도를 같이 씁니다. 그러면 같은 릴리스 파일을 API 없이 바로 받고, 체크섬 확인은 그대로 합니다. `GITHUB_TOKEN` 을 두면 한도도 늘어납니다. |
| 에이전트 설치가 *Get-FileHash is not recognized* 로 실패 | 앱을 PowerShell 7 터미널에서 켜서, 그 모듈 경로가 Windows PowerShell 을 깨뜨린 경우입니다. 이제 앱이 시작할 때 정리합니다 — 앱을 한 번 다시 켭니다. |
| **분석 엔진 · 설치 필요** | 레퍼런스 모드가 원본 저장소를 분석할 때 쓰는 엔진 두 가지(구조 지도·진입점 규칙)입니다. **설치** 를 누르면 공식 배포본을 체크섬으로 확인해 설치합니다. |
| `develop` 에서 하던 커밋 안 된 변경이 없어졌다 | `develop` 에서 작업을 시작하면 그 변경을 실행 이름을 붙인 stash 에 보관합니다 (`git stash list`). `develop` 으로 돌아가 `git stash pop` 하면 됩니다. |
| **합치기** 에 *충돌* 이 뜬다 | 아무것도 바꾸지 않았습니다. 직접 합치거나 작업 브랜치를 고친 뒤 다시 — 충돌한 파일이 메시지에 나옵니다. |
| 첨부한 링크에 **로그인 필요** 가 뜬다 | 앱이 그 페이지를 앱 안의 브라우저 창으로 엽니다 — 로그인한 뒤 **이 문서 가져오기** 를 누릅니다. 이런 링크를 남긴 채 시작하면 먼저 로그인을 요청합니다. |
| 터미널 창이 잠깐 뜬다 | 자식 프로세스는 창 없이 띄웁니다. 확인된 원인은 에이전트 CLI 의 자동 업데이트가 앱의 로그인 확인(약 15분마다) 때 자기 콘솔을 연 것이었고, 이제 앱이 띄우는 CLI 는 자동 업데이트를 끕니다. CLI 업데이트는 터미널에서 직접 하세요. |
| macOS: Finder 로 열면 에이전트를 못 찾는다 | 앱이 시작할 때 로그인 셸의 PATH(Homebrew·nvm·`~/.local/bin`)를 읽어 씁니다. |
| 레퍼런스 분석이 권한(DACL) 오류나 *could not load saved runtime settings* 로 실패 | 구조 지도 엔진은 상위 폴더에 다른 계정의 쓰기 권한이 있는 폴더를 거부합니다. 앱은 엔진 폴더를 `~/.beom-workbench` 아래에 둡니다 — 데이터 폴더를 옮긴 경우에만 생깁니다 (`BEOM_WORKBENCH_HOME` 을 `AppData` 아래로 두는 등). 사용자 폴더 아래에 두세요. |
| 빌드에 필요한 도구가 없다 (예: Windows 에서 Rust 저장소의 OpenSSL) | 폴더를 고르면 새 작업 화면이 없는 빌드 도구(Rust·OpenSSL·Node.js·JDK·Go)와 **설치** 단추(winget·Homebrew)를 보여 줍니다. 에이전트도 처음에 알고 시작해 중간에 멈추지 않습니다. OpenSSL 을 설치하면 에이전트에게 `OPENSSL_DIR` 을 알아서 넘깁니다. |
| 검증이 "서버에 연결하지 못함" 으로 실패 | 검증할 때 서버가 떠 있지 않았습니다 — 대개 빌드가 안 됨(빌드 준비물 없음). 검증 탭이 원인별로 묶어 보여 줍니다. |
| "앱 밖에서 바뀐 결정이 있어 멈췄습니다" | 아래 *안전 원칙* 참고 — 변경 탭을 확인하고 **확인했음** 을 누르면 이어 갑니다. |

## 알려진 한계

| 한계 | 대응 |
|---|---|
| 차등 검증은 돌려 본 입력만 증명 | 입력 자동 변형·커버리지로 범위를 넓히고, 남은 범위는 근거의 limitations 에 기록. 성능은 비교하지 않음 |
| 커버리지는 "실행됐다"만 증명 | 어떤 분기·입력인지는 케이스로 따로 확인 |
| 이름 기반 호출 관계는 후보 | 언어 서버(L1)나 실행(L3)으로 확인해야 근거 |
| 동적 디스패치·리플렉션·매크로 생성 코드 | 자동으로 미확인 처리 |
| 데이터 흐름 엔진 첫 실행이 느림 (1만 줄 Java 약 15분) | 캐시, `dataflow --build-only` 로 미리 생성 |
| CLI 는 호출마다 언어 서버를 새로 띄움 | 같은 언어는 프로세스 간 줄 세움. MCP 모드는 서버를 재사용 |
| 설정값에 따라 바뀌는 경로 | 기본값으로 펼치고 미확인으로 표시 |
| 네이티브 앱 화면 확인은 Windows 만 | macOS·Linux 는 웹 화면·CLI·함수 케이스로 확인. 확인하는 동안 앱 창이 잠깐 화면에 뜸 |
| 예전 한글(.hwp)·오피스 97-2003 파일은 읽지 못함 | 첨부할 때 거절하고 HWPX·docx·pptx·xlsx 로 저장하라고 안내 |
| Gemini(agy)의 스트리밍 출력 형식이 공개 문서에 없음 | 이름이 조금 달라도 받아들이게 읽음 (실험적) |
| 로컬 프로그램이라 같은 권한으로 작정하고 기록을 위조하면 막을 수 없음 | 위조 시도는 게이트 실패로 드러남. 최종 판정은 깨끗한 환경에서 다시 실행 가능 |

## 보안 신고와 기여

- 취약점은 GitHub 의 **Report a vulnerability**(Security 탭)로 비공개 신고해 주세요 — [SECURITY.md](SECURITY.md).
- 버그 제보와 기능 요청은 이슈로 받습니다. PR 은 제안으로 받지만 그대로 합치지는 않습니다 — 라이선스상 수정본을 허용하지 않아,
  받아들인 변경은 관리자가 반영합니다. [CONTRIBUTING.md](CONTRIBUTING.md) 를 보세요.
- 브랜치: `main` 은 배포본(버전마다 `vX.Y.Z` 태그)입니다. 작업은 `main` 에서 만든 짧은 `feature/…`·`fix/…` 브랜치에서 하고, 그 브랜치를
  `develop`(실험 공간)에 합쳐 시험한 뒤 같은 브랜치를 PR 로 `main` 에 합쳐 적용합니다 (Windows·macOS·Linux CI 통과). `develop` 은 `main` 에
  합치지 않습니다 — 필수 점검 *branch-policy* 가 `develop` 에서 왔거나 `develop` 전용 커밋이 섞인 `main` PR 을 막고, `develop` 에는
  `feature/`·`fix/`·`hotfix/` 브랜치만 합치게 합니다. `main`·`develop` 은 보호돼 관리자만 바꿉니다.
